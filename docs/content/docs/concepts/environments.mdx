An **environment** is a single microVM and the task running inside it. You create
one with a resource spec (CPU/memory/storage, and optionally GPU), an optional
manifest and secrets, and an optional startup script. Fuse picks a host, boots the
VM, uploads your files, starts the in-guest agent, and tracks it through its
lifecycle. A background reconcile loop catches orphans and stuck VMs.

## Lifecycle states

```
provisioning -> running -> draining -> destroying -> destroyed
                                                    -> failed
                                       destroying -> destroy_failed -> destroying (on DELETE)
```

- **provisioning**: a host has been picked and the VM is booting.
- **running**: the VM is up and the in-guest agent is reachable.
- **draining**: a graceful two-phase teardown has started: the agent's drain
  command has been invoked so the workload can flush/stop cleanly, but the VM is
  **not yet destroyed**. Only running environments can be drained; any other state
  returns a conflict.
- **destroying / destroyed**: the VM is being (or has been) torn down.
- **destroy_failed**: with restate on (`FUSE_RESTATE_MODE=self` or `cloud`), a
  destroy whose host kept failing after every retry. The VM may still exist on
  its host and still counts against the host's capacity. The last error is on
  the environment and in a `destroy` dead letter. `DELETE` it again to retry.
- **failed**: provisioning or an operation failed.

`destroyed` and `failed` are terminal states you only ever observe on the event
stream: by the time either is published the environment record has already been
removed, so a follow-up `fuse environment get <id>` returns 404 rather than a record
carrying the failure. The error text survives on the task record, and `--follow` (or
`fuse environment watch`) prints it inline, so read it there rather than expecting it
on the environment.

Drain itself does not destroy the VM. A subsequent explicit destroy call removes
it. If none arrives, the [reconcile loop](/docs/concepts/reconcile#stuck-draining)
destroys an environment that has been draining longer than the draining timeout,
5m30s by default (`--draining-timeout` on the orchestrator).

## Health is not a state

`running` means the VM is up and the guest agent is reachable. It does not mean
your workload is serving: nothing dials it.

An environment created with a [`healthcheck`](/docs/concepts/fusefile#healthcheck)
carries a separate `health` field, whose `state` is `starting`, `passing`, or
`failing`. It is deliberately not folded into the lifecycle vocabulary above: that
set is closed and every SDK reasons about it, and an unhealthy environment is
still a running one.

Nothing is destroyed for a failing probe. The field reports, and
[`fuse up --wait-healthy`](/reference/cli/up#waiting-for-healthy) is what turns
it into a gate. An environment that declared no healthcheck never carries the
field at all.

## Creating one

Two paths: compile a [Fusefile](/docs/concepts/fusefile) with `fuse up`, or
create one directly with a raw resource spec:

```bash
fuse environment create --task-id my-task --cpus 2 --ram-mb 2048 --storage-gb 10
```

`create` schedules orchestrator-wide. The CLI's active host selection does not pin
placement; use `--region` to influence it.

## Watching progress

```bash
fuse environment watch <id>     # stream state transitions until terminal
fuse environment create --follow ...  # same, inline with create
```

Both are backed by the same mechanism as the HTTP API's live event stream (Server-Sent
Events), no polling loop involved.

## Draining and destroying

```bash
fuse environment drain <id>      # running -> draining (graceful, phase 1)
fuse environment destroy <id>    # tear down (phase 2, or from any state)
```

## Long operations and retries

Create, destroy, fork, migrate, drain, snapshot create and snapshot restore
run on the orchestrator as **operations**, off the request that started them.
The request waits for its operation up to the server's attach bound, 10
seconds below its `-write-timeout` (50s by default), and answers as it always
has when the operation finishes in time. One that takes longer, a cold boot
with a slow startup script or a cross-host migrate, is answered `202` with an
operation id instead, and keeps running. `?wait=false` asks for the `202` at
once, and `?wait=30s` waits that long (capped at the bound). Every answer an
operation gives carries its id in a `Fuse-Operation-Id` header.

The SDKs and the CLI follow a `202` for you, polling
[`GET /v1/operations/{operationId}`](/reference/api) until the operation
finishes, so a long call simply takes longer to return. Leaving early (a
cancelled context, an interrupted CLI) leaves the operation running; pick it
up with [`fuse operation wait`](/reference/cli/operation/wait) or the SDKs'
`operations.wait`. While a migrate runs, its operation's `step` reports how
far it got: `snapshot`, `transfer`, `delta`, `boot`, then `cutover`.

An `Idempotency-Key` header makes a mutating call safe to retry. A retry of
the same request with the same key attaches to the first call's operation
instead of running again, waiting for it if it is still running or replaying
its answer (with `Idempotent-Replayed: true`) if it finished. That is what
turns "the connection dropped during a create" from a guess into a second
call that cannot provision a second environment. The rules:

- Keys are scoped to the credential that sent them, 1 to 255 visible ascii
  characters.
- The same key with a different request is a `409` `conflict`,
  `details.reason` `idempotency_key_reused`.
- A finished operation and its key are kept for 24 hours. One that finished
  with a 5xx is not kept, so its retry runs again.
- Operations and keys live in the orchestrator's memory, and a restart forgets
  them. With [restate](/docs/cloud/orchestrator-deploy#restate) on, a create,
  destroy, snapshot or restore also hands the key to restate as the invocation's
  idempotency key, so a retry after a restart still attaches to the same
  invocation. A destroy that already finished is the exception: its vm is
  gone, so that retry answers `404`. Fork, migrate and drain have no such
  fallback.

The SDKs send a random key on every call and take your own for retries:
`WithIdempotencyKey` in [Go](/reference/go/operations), `idempotencyKey` in
[TypeScript](/reference/typescript/operations) and `idempotency_key` in
[Python](/reference/python/operations). The CLI sends a fresh key on every
invocation, so running a command again is a new request, not a retry of the
last one.

## Forking

```bash
fuse environment fork <id> --comment "branch for experiment"
```

Forking creates a new environment from an existing one's state, either by taking a
fresh snapshot or reusing an existing one via `--reuse-snapshot`. The source keeps
running and is not modified.

The fork is a full environment of its own: its own ID, its own IP and ports, and its
own guest credentials. Because it boots a copy of the source's disk, it starts out
with the source's filesystem contents, but it is re-issued a fresh auth token on
creation, so the two environments never share a secret.

The source must be **running**; forking an environment in any other state fails.

A fork always lands on the **same host** as its source (the seed snapshot lives on
that host's disk), and it is charged against that host's capacity like any other
environment. It does **not** go through the scheduler, though, and no capacity check
runs on that host: forking onto a host with nothing left succeeds and overcommits it,
so keep an eye on the source host's headroom rather than relying on admission
control to stop you.

A fork cold-boots the snapshot's disk rather than resuming the source's memory:
expect a normal boot, not a sub-second resume. That is true of
[live snapshots](/docs/concepts/snapshots#two-kinds) too, fork reads a snapshot's
rootfs and nothing else, so forking one gives you its disk half without the
memory it captured.

See [Snapshots](/docs/concepts/snapshots): forking is unavailable wherever
snapshotting is (i.e. QEMU/GPU environments).

## Rotating guest credentials

```bash
fuse environment rotate-token <id>
```

Generates fresh TLS credentials and an auth token for a running environment, writes
them into the guest's credential files, and persists the new encrypted token on the
orchestrator, all without recreating the VM.

Rotation requires the environment to be **running**, and it requires an orchestrator
started with a 32-byte `TOKEN_ENCRYPTION_KEY`, a dev-mode orchestrator without one
generates no per-VM credentials in the first place and so has nothing to rotate.

:::warning[Known limitation]
Rotation does **not** take effect inside a running guest. `fused` reads its auth
token exactly once at process start and has no credential poller, so it keeps serving
the old token until it is restarted. Treat rotate-token as updating the stored and
on-disk copies, not as a way to revoke a leaked token.
:::
